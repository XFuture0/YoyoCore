# 管理器基类

*写代码嘛，总要有点「偷懒」的智慧。*

在 Unity 开发中，我们经常会遇到这样的场景：需要一个全局唯一的对象来管理某些功能，比如音频管理、资源加载、事件分发等等。这时候，**单例模式（Singleton Pattern）** 就成了我们的老朋友。

Yoyo Core 框架提供了两个管理器基类，分别对应两种不同的需求场景。

## 非继承 Mono 的管理器基类

**BaseMgr<T>** 适用于那些不需要挂载在 GameObject 上的管理器。

**诞生背景**

在 Unity 中，并不是所有的管理器都需要生命周期函数（如 Update、Start 等）。比如一个纯粹的数据管理器、配置管理器，它们只需要一个全局访问点，不需要参与 Unity 的游戏循环。这时候，强行继承 MonoBehaviour 反而会增加不必要的开销。

**使用方法**

```csharp
// 示例代码
public class MyMgr : BaseMgr<MyMgr>
{
    // 构造函数必须是私有的
    private MyMgr() { }

    public void DoSomething()
    {
        Debug.Log("Doing something...");
    }
}

// 使用
MyMgr.Instance.DoSomething();
```

**技术细节**

这个基类采用了**双检锁（Double-Check Locking）**机制来保证线程安全：

1. 第一次检查 instance 是否为 null，避免不必要的加锁
2. 使用 lock 确保多线程环境下只有一个实例被创建
3. 第二次检查确保在等待锁的过程中没有其他线程创建了实例

```csharp
// 双检锁实现
if (instance == null)
{
    lock (lockobj)
    {
        if (instance == null)
        {
            // 创建实例
        }
    }
}
```

另外，它通过反射来获取私有构造函数，这意味着你的管理器**必须有一个无参的私有构造函数**，否则会抛出错误。

## 继承 Mono 的管理器基类

**BaseMgr_Mono<T>** 适用于需要挂载在 GameObject 上的管理器。

**诞生背景**

有些管理器需要参与 Unity 的生命周期，比如需要在 Update 中轮询检测、需要使用协程等。这时候就需要继承 MonoBehaviour，但又希望保持单例的便利性。

**使用方法**

```csharp
// 示例代码
public class MyMonoMgr : BaseMgr_Mono<MyMonoMgr>
{
    protected override void Awake()
    {
        base.Awake();
        // 你的初始化代码
    }

    void Update()
    {
        // 每帧执行
    }
}
```

**技术细节**

这个基类有几个值得注意的地方：

**自动创建 GameObject**

当第一次访问 Instance 时，如果实例不存在，它会自动创建一个 GameObject 并挂载组件：

```csharp
GameObject obj = new GameObject();
obj.name = typeof(T).ToString();
instance = obj.AddComponent<T>();
DontDestroyOnLoad(obj);
```

**Awake 中的处理**

在 Awake 中做了两件事：
1. 如果 instance 已经存在（说明是重复创建的），销毁自身
2. 否则设置 instance 并标记为 DontDestroyOnLoad

这保证了即使场景中有多个同名 GameObject，也只有一个实例会被保留。

## 如何选择

**场景：不需要 Update/协程**
推荐基类：BaseMgr<T>

**场景：需要 Update/协程**
推荐基类：BaseMgr_Mono<T>

**场景：纯数据/逻辑管理**
推荐基类：BaseMgr<T>

**场景：需要与 Unity 生命周期交互**
推荐基类：BaseMgr_Mono<T>

## 注意事项

1. **构造函数必须是私有的**，这是单例模式的基本要求
2. 使用 BaseMgr_Mono 时，**不要手动在场景中放置**该管理器的 GameObject，让它自动创建即可
3. 两个基类都使用了 DontDestroyOnLoad，这意味着管理器在场景切换时会被保留

## 技术地位和意义

这两个基类是整个 Yoyo Core 框架的基石。它们提供了一个统一的管理器创建模式，让开发者可以专注于业务逻辑，而不必每次都重复编写单例代码。同时，通过区分 Mono 和非 Mono 场景，也避免了不必要的性能开销。

*毕竟，好的框架就是要让开发者「偷懒」偷得心安理得嘛。*
